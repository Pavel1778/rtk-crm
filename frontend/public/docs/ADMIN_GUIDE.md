# Руководство администратора RTK CRM

## 1. Роль администратора

Администратор отвечает за пользователей, справочники, этапы workflow и
доступность системы. Операционные действия выполняются после проверки прав и
бизнес-ограничений.

## 2. Пользователи

Управление пользователями находится в разделе **Пользователи** (вкладка
«Пользователи»). Для каждого пользователя задаются email, имя, роль и
активность. При деактивации доступ закрывается без удаления истории.

Создание: заполните ФИО, email, пароль и роль, затем «Добавить». Роль и
активность можно менять прямо в списке; удаление доступно для любой учётной
записи, кроме собственной.

Минимальные роли:

- **КАМ** — работа с взаимодействиями;
- **Руководитель** — просмотр отчётов, контроль процесса и назначение КАМ;
- **Администратор** — настройки и справочники.

Руководитель и администратор назначают ответственного КАМ при создании
взаимодействия и могут передать существующую карточку другому сотруднику.
КАМ работает только со своими взаимодействиями: чужие карточки недоступны
по прямому id.

## 3. Этапы workflow

Откройте **Пользователи** и перейдите на вкладку **Этапы воркфлоу**.
Конструктор показывает все этапы, включая выключенные. На каждой строке
доступны сортировка, редактирование, переключатель активности и удаление.
Переключатель **B2B / B2C** на той же вкладке задаёт воронку: у каждой свой
набор этапов.

![Конструктор workflow](/docs/images/08-workflow-constructor.png)

### Включение и выключение

Переключатель работает в обе стороны. При ошибке интерфейс откатывает
оптимистичное изменение. Этап с активными взаимодействиями нельзя отключить:
сначала перенесите взаимодействия либо удалите этап с выбором целевого этапа.

### Переименование и сортировка

Измените название в строке этапа и подтвердите сохранение. Для изменения
порядка перетащите строку за область drag-and-drop.

### Удаление с переносом

Перед удалением система показывает количество активных и всех взаимодействий.
Если данные есть, выберите целевой этап. Перенос выполняется до удаления
исходного этапа.

## 4. Справочники

В разделе **Справочники** поддерживаются вузы, ИТ-направления и ИТ-продукты.
Перед удалением проверьте связанные данные. Не помещайте персональные данные
в поле комментария без правового основания.

![Справочники](/docs/images/05-directories.png)

## 5. Импорт и экспорт

Экспорт отчётов выполняется на странице **Отчёты** в XLSX, XLS или PDF.
Для массовой загрузки используйте импорт в разделе **Справочники**: диалог
принимает XLS/XLSX и JSON, показывает предпросмотр и предлагает сопоставить
колонки файла с полями справочника. Перед запуском сделайте резервную копию и
проверьте сопоставление — строки с ошибками можно пропустить, импортировав
только валидные.

![Импорт справочников из XLSX](/docs/images/06-import-xlsx-mapping.png)

## 6. Интеграция с LMS и CMS

Вкладка **Интеграция** описывает обмен с внешними системами заказчика.
Администратор здесь проверяет контракт и управляет загрузкой пакетов.

Порядок действий:

1. Откройте **Интеграция** и посмотрите **схему обмена** — перечень полей
   контракта и обязательность каждого.
2. Вставьте пакет JSON в поле ввода либо нажмите **Загрузить пример**.
3. Нажмите **Предпросмотр**: пакет проверяется по контракту без записи в
   базу. Так проверяют формат перед реальным импортом (dry-run).
4. Нажмите **Импортировать**, если предпросмотр не показал ошибок.

Импорт идемпотентен по `contract_number`: повторная загрузка того же пакета
обновляет существующее взаимодействие, а не создаёт второе. Это позволяет
безопасно повторять обмен после сбоя сети.

Вкладка также формирует **исходящий пакет** — выгрузку для передачи во
внешнюю систему в формате контракта.

В прототипе интеграция работает через mock-адаптер: он возвращает
детерминированные данные по тому же контракту. Подключение реальных LMS и CMS
выполняется реализацией того же интерфейса, без изменений в остальной системе.

![Интеграция с LMS и CMS](/docs/images/11-integration.png)

## 7. Аудит и безопасность

Изменения записываются middleware аудита (POST/PUT/PATCH/DELETE). Журнал
открывается в разделе **Журнал**: время, сотрудник, действие, сущность и IP.
Доступны фильтры по действию, сущности и сотруднику, сортировка — от свежих
записей. При расследовании укажите пользователя, сущность, время и
идентификатор операции. Не передавайте JWT, пароли и `.env` в тикетах или
репозитории.

В рабочем контуре используйте HTTPS, ограниченный CORS, JWT/RBAC и
минимальные права базы данных.

![Журнал аудита](/docs/images/12-audit-log.png)

## 8. Резервное копирование

Для Yandex Cloud ежедневный backup запускается
`infra/yandex-cloud/backup.sh`. По умолчанию хранятся последние 7 дней.
Периодически проверяйте восстановление на тестовой базе.

## 9. Устранение неисправностей

**Пользователь не входит:** проверьте активность учётной записи, CORS и
состояние backend `/api/health`.

**Экспорт не скачивается:** убедитесь, что запрос выполняется из авторизованной
сессии и в ответе присутствует `Content-Disposition`.

**Этап не отключается:** это защита при наличии активных взаимодействий.

**Пустые графики:** проверьте диапазон данных, активность этапов и ответ
`GET /api/reports`.
